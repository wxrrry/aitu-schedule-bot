### 13.10.26 — API и REST API, JSON

#### Что такое API
**API (Application Programming Interface)** — программный интерфейс приложения: набор указаний, которые оно может выполнить по запросу других приложений. Указаниями могут быть выполнение функции, предоставление или получение данных.

#### Зачем нужен
- Даёт универсальный доступ любым клиентам (десктоп, мобильный) — одинаковые методы и эндпоинты для всех.
- Выступает прослойкой-защитой данных: наружу торчит только разрешённое.
- Отвечает на вопрос: «Как к моей системе можно обратиться?»

#### Из чего состоит обращение
1. Сама операция, которую можно выполнить.
2. Данные на вход.
3. Данные на выход (контент данных или сообщение об ошибке).

#### Стили API
REST, HATEOAS, SOAP, GraphQL, gRPC. Разбор REST и JSON — ниже (расширено по учебнику).

#### REST подробно
**REST (Representational State Transfer)** — передача состояния представления. Не протокол, а архитектурный стиль: набор ограничений, которым следует API.
- **Ресурсы**: всё — ресурс с адресом (URI). Не «функции», а «сущности»: `/users/5`, `/tickets?status=open`.
- **Методы HTTP = операции**: GET (прочитать), POST (создать), PUT/PATCH (обновить целиком/частично), DELETE (удалить).
- **Stateless**: сервер не помнит прошлые запросы — каждый запрос самодостаточен (авторизация летит в каждом: токен/JWT).
- **Представление**: один ресурс отдаётся в разных форматах (обычно JSON), клиент выбирает заголовком.
- **Коды ответа**: 2xx успех (200 OK, 201 Created), 4xx вина клиента (400, 401, 404), 5xx вина сервера (500).
Пример: `GET /api/equipment/3` → `200 OK` + JSON паспорта техники.

#### JSON подробно
**JSON (JavaScript Object Notation)** — текстовый формат обмена данными. Почему главный в REST: читаем человеком, понимает любой язык, лёгкий.
- Типы: объект `{}`, массив `[]`, строка, число, `true/false`, `null`.
- Пример:
```json
{
  "id": "demo-eq-1",
  "name": "Пароконвектомат Rational",
  "status": "NEEDS_CHECK",
  "temperatures": [4.2, 5.1],
  "warranty": null
}
```
- Правила: ключи всегда в двойных кавычках, запятая между элементами (но не после последнего), без комментариев.

#### Как связано: API → REST → JSON
API — общее понятие (любой программный интерфейс). REST — самый популярный стиль проектирования API для веба. JSON — самый популярный формат данных внутри REST. Связка покрывает ~80% интеграций, с которыми работает внедрение и поддержка КС.

Принципы REST api

Отсутствие состояния. Каждый запрос от клиента к серверу обрабатывается независимо от пердыдущих запросов. Сервер не хранит информацию о состоянии клиента, что упрощает обработку запросов и повышает отказоустойчивость системы.

#### 6 базовых принципов (ограничений) REST API
REST опирается на 6 обязательных принципов архитектуры (по Филдингу):

1. **Клиент-Серверная архитектура (Client-Server)**
   Чёткое разделение ответственности: интерфейс пользователя (клиент) изолирован от хранения данных и бизнес-логики (сервер). Это позволяет развивать фронтенд (React, мобильное приложение) и бэкенд (Express, FastAPI) независимо.
2. **Отсутствие состояния (Stateless)**
   Каждый запрос от клиента к серверу должен содержать абсолютно всю информацию, необходимую для его обработки. Сервер не хранит между запросами сессионный контекст клиента.
   > **Как работает в бою:** Аутентификация передаётся в каждом запросе в заголовке `Authorization: Bearer <JWT-токен>`. Если один сервер упадёт, другой сразу сможет обработать запрос без репликации сессий.
3. **Кэшируемость (Cacheable)**
   Ответы сервера должны быть явно помечены как кэшируемые или некэшируемые (через заголовки `Cache-Control`, `ETag`, `Expires`), чтобы клиент или промежуточные прокси могли повторно использовать данные без лишних сетевых вызовов.
4. **Единообразие интерфейса (Uniform Interface)**
   Главное ограничение REST, делающее API предсказуемым:
   - Идентификация ресурсов по стабильным URI (например, `/api/v1/equipment/42`).
   - Манипуляция через стандартные HTTP-методы (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`).
   - Самоописываемые сообщения (заголовки `Content-Type: application/json`).
   - HATEOAS (гипермедиа как двигатель состояния — опциональные ссылки на следующие действия).
5. **Слоистая система (Layered System)**
   Клиент обычно не знает, общается ли он напрямую с целевым сервером или с промежуточным узлом (Nginx reverse-proxy, API Gateway, балансировщик нагрузки, CDN, WAF-файрвол). Промежуточные слои повышают масштабируемость и безопасность.
6. **Код по требованию (Code on Demand — опционально)**
   Сервер может временно расширить функционал клиента, отправив исполняемый код (например, JavaScript-скрипт или WebAssembly). Единственное необязательное ограничение REST.

> [!example] Как это устроено на практике в проекте [[🧑‍🍳 Моя Кухня]]
> - **Стек:** Express API + Nginx (слоистая система) + MySQL ([[🏗️ 03_Архитектура-и-стек]]).
> - **Stateless:** Вся авторизация идёт по JWT (7 дней) без серверных сессий в памяти.
> - **Ресурсы и методы:** `GET /tickets` — список заявок, `POST /tickets` — создание, `GET /equipment/:id` — паспорт единицы оборудования.
> - **Коды ответов:** `200` при успехе, `201` при создании записи инвентаризации, `401` при невалидном токене.

> [!abstract] Резюме для экзамена (TL;DR)
> **REST** — это не протокол и не библиотека, а архитектурный стиль работы через HTTP. Ресурсы именуются существительными (`/users`), действия задаются глаголами HTTP (`GET`, `POST`, `PUT`, `DELETE`), сервер не помнит состояние клиента (**Stateless**), а данные чаще всего пакуются в **JSON**.
